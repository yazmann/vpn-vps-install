# VPN VPS Setup — подробная документация

[← Краткая инструкция](../README.md)

Установщик чистого Ubuntu VPS с четырьмя транспортами. Vision и XHTTP работают через 3x-ui и REALITY Self-steal. AmneziaWG и Hysteria 2 запускаются как самостоятельные службы systemd.

## Главное

- [VLESS + TCP/REALITY + XTLS Vision](https://github.com/XTLS/Xray-core) по умолчанию либо выбираемый VLESS + XHTTP/REALITY; оба используют Self-steal на TCP/443.
- [NGINX](https://github.com/nginx/nginx) с сайтом-заглушкой на том же домене, HTTP/2 по ALPN и локальным TLS fallback — для схемы Self-steal.
- TLS-сертификат [Let's Encrypt](https://letsencrypt.org/) обновляется через постоянный webroot Nginx; TCP/80 сохраняет ACME challenge и перенаправляет остальные запросы на HTTPS. Также настраиваются UFW, [BBR](https://www.kernel.org/doc/html/latest/networking/bbr.html), отключение IPv6 и ежедневные обновления безопасности.
- Перед установкой VPN мастер восстанавливает незавершённое состояние `dpkg`, обновляет индексы репозиториев и выполняет полное обновление всех установленных пакетов Ubuntu с проверкой целостности пакетной базы.
- Мастер безопасности сохраняет текущий root/SSH-доступ по умолчанию, чтобы не заблокировать администратора; отдельно доступны усиливающие режимы root только по ключу и нового sudo-пользователя с отключением прямого входа root. Fail2ban jail для `sshd` включается во всех режимах.
- По умолчанию включаются ежедневные обновления безопасности и еженедельное обслуживание Ubuntu с условной перезагрузкой. Мастер также предлагает режим ежедневных обновлений безопасности и ручной режим.
- Подписки для [HAPP](https://github.com/Happ-proxy/happ-desktop), [INCY](https://incy.cc/) и [Mihomo](https://github.com/MetaCubeX/mihomo) с правилами маршрутизации [RoscomVPN](https://github.com/hydraponique/roscomvpn-routing).
- [Cloudflare WARP](https://www.cloudflare.com/warp/) — дополнительный выход для российских ресурсов (домены и IP): сайт видит адрес WARP вместо адреса VPS. Остальной трафик использует обычный выход. Включён по умолчанию, отключается ответом `no`.
- Самостоятельный VPN-сервер или удалённая нода для существующей панели.
- Панель по умолчанию слушает `127.0.0.1`. Для доступа через сеть доступны allowlist одного IPv4 и явный публичный режим. Случайный порт и путь используются во всех режимах.
- Установщик получает свежие стабильные релизы 3x-ui, Xray-core и Hysteria 2, сверяет SHA-256 по метаданным GitHub. Certbot и системные зависимости идут из APT. Для AmneziaWG подключается официальный подписанный PPA. Файлы RoscomVPN берутся из одной актуальной ревизии и сверяются с хешами Git.

## Требования

Обязательно:

- Чистый Ubuntu 22.04+ с systemd на `x86_64`/`amd64`, `aarch64`/`arm64`, `armv7l` или `s390x`.
- Первоначальный root-доступ, публичный IPv4 и исходящий доступ в Интернет для APT, GitHub и Let's Encrypt.
- Домен у любого DNS-провайдера с единственной прямой A-записью на IPv4 VPS. AAAA и DNS-прокси использовать нельзя.
- Свободные и доступные извне TCP/80, TCP/443 и текущий SSH-порт.
- Для Hysteria 2 требуется UDP/443. Для AmneziaWG откройте показанный установщиком UDP-порт в firewall провайдера. Нужны заголовки установленного ядра и возможность загрузить AmneziaWG DKMS. При обновлении ядра перезагрузка может потребоваться до возобновления установки.
- Доступные Ubuntu-репозитории `main`, `universe` и `security`.
- Отсутствие установленных 3x-ui, Nginx, `/root/.acme.sh`, старого state этого проекта и настроенных правил UFW.

Опционально:

- SSH-ключ — только для двух key-only режимов. Без ключа можно явно сохранить текущую SSH-политику.
- Доверенный публичный IPv4 — только для режима allowlist панели.
- Главная 3x-ui панель — только для режима удалённой ноды.
- WARP и Tailscale не обязательны.

Установщик сам ставит системные пакеты. Существующий ключ можно перенести из `/root/.ssh/authorized_keys` или вставить вручную.

## Установка

Выполните [команды установки](../README.md#установка) от `root`. Мастер предлагает Vision и панель на localhost по умолчанию, сохраняет действующую SSH-политику и включает ежедневные обновления безопасности и еженедельное обслуживание. После установки настройки выводятся на экран и сохраняются в файле `/root/xhttp-vps-result-*.txt` с правами `0600`.

### Выбор безопасности при установке

| Настройка | Варианты | Значение по умолчанию и рекомендация |
|---|---|---|
| Доступ к панели | Весь Интернет, один доверенный публичный IPv4 или только `127.0.0.1` | Localhost через SSH/Tailscale. Для удалённой ноды подходит allowlist IP главной панели. |
| SSH | Оставить текущую политику; `root` только по ключу; новый sudo-пользователь по ключу | Текущая root/SSH-политика сохраняется, чтобы исключить случайную блокировку доступа. Два следующих пункта последовательно усиливают защиту. |
| 2FA | Не настраивать сейчас; показать инструкцию после установки | Для публичной панели рекомендуется как дополнительная защита, но включается пользователем в интерфейсе 3x-ui. |
| Обновления | Еженедельное обслуживание, ежедневные обновления безопасности или ручной режим | Еженедельное обслуживание с ежедневными обновлениями безопасности. |

Публичная панель удобна с любого устройства, но её секретный путь не заменяет аутентификацию. Используются HTTPS, случайный порт, 128-битный путь, случайные учётные данные и встроенное ограничение попыток входа 3x-ui. Если панель доступна из Интернета, 2FA рекомендуется как дополнительный уровень защиты, но остаётся отдельной опцией пользователя после первого входа. В allowlist/private-режимах сетевая поверхность дополнительно уменьшается.

Если выбран один из key-only режимов, не закрывайте исходную root-сессию, пока во втором терминале не проверите выбранный вход (и `sudo` для нового администратора):

```bash
ssh -p SSH_PORT SELECTED_USER@vpn.example.com
sudo -n true
```

Пароль нового Linux-пользователя заблокирован; `sudo` разрешён без пароля, потому что сервер принимает только заранее установленный SSH-ключ. Это означает, что защита приватного ключа критична: используйте локальную passphrase и блокировку устройства. Если выбран режим сохранения текущей SSH-политики, установщик явно помечает hardening как `SKIP` и не заявляет, что парольный/root-доступ безопасен.

## Управление

Чтобы снова открыть меню установщика:

```bash
sudo /root/install-xhttp-vps.sh
```

- Для установленного сервера пункт `1` показывает настройки, пункт `2` проверяет и восстанавливает конфигурацию, пункт `3` окончательно удаляет VPN без архива.
- Если установка прервалась: `sudo /root/finish-xhttp-vps.sh`. При незавершённом bootstrap он продолжает установщик с прежними параметрами, затем возвращается к настройке панели. Повторный ввод домена/паролей не требуется.
- Храните скрипты из одного коммита рядом. Возобновление и удаление используют журнал файлов, записанный при установке.

## Доступ к панели с компьютера и телефона

По умолчанию панель доступна с компьютера и телефона по сохранённому публичному HTTPS URL со случайным портом и секретным путём. Не публикуйте полный URL и учётные данные. При желании усилить сетевую изоляцию выберите `Private localhost`: панель останется доступна через работающий SSH или приватную overlay-сеть.

Разовый доступ через SSH-туннель:

```bash
ssh -p SSH_PORT -L PANEL_PORT:127.0.0.1:PANEL_PORT SELECTED_USER@vpn.example.com
```

Замените `PANEL_PORT` числом из результата установки и, пока SSH-сессия открыта, перейдите по сохранённому локальному URL панели. В Termius на телефоне создайте Local Port Forwarding с destination host `127.0.0.1`, destination port и local port равными порту панели. Поскольку сертификат панели выпущен на домен, браузер при обращении к `127.0.0.1` может показать несовпадение имени; для постоянного мобильного доступа лучше Tailscale Serve.

После установки Tailscale на VPS и телефон и подключения их к одному tailnet выполните на VPS:

```bash
tailscale serve --bg https+insecure://127.0.0.1:PANEL_PORT
tailscale serve status
```

Открывайте выданный адрес `https://имя-узла....ts.net/PANEL_PATH/` через приложение Tailscale. Используется приватный **Serve**, не публичный Funnel. Установщик намеренно не ставит Tailscale и не получает доступ к вашему tailnet. Правила ACL tailnet должны разрешать доступ только вашим администраторским устройствам.

Режим `Allow one trusted public IPv4` подходит для связи удалённой ноды с главной панелью. Для телефона с меняющимся мобильным IP он неудобен. Для публичной панели рекомендуется включить 2FA в 3x-ui как дополнительную защиту и хранить recovery codes отдельно.

## Удаление без архива

Перед удалением сохраните нужные данные. Для изменения расхода памяти переустановка не требуется — используйте процедуру ниже.

1. Запустите `sudo /root/install-xhttp-vps.sh`.
2. Выберите пункт `3` и введите точное подтверждение `DELETE домен`.

Перед установкой сохраняются только исходные версии управляемых файлов и журнал `/root/xhttp-managed.*`. При удалении созданные VPN-файлы, данные 3x-ui, сайт, сертификат, result/state и сам журнал удаляются без архива, а существовавшие до установки файлы возвращаются на место.

Пакеты, swap, созданный Linux-администратор, выбранная SSH policy, SSH-правило UFW и общий ACME-клиент остаются: автоматическое возвращение root/password login при удалении VPN было бы небезопасным. Удаляются только firewall-правила с меткой данной установки. `purge` и `autoremove` не запускаются. Для повторной чистой установки используйте свежий VPS.

У старых установок без журнала автоматическое удаление блокируется: state-файл не доказывает происхождение всех файлов. Не создавайте журнал задним числом из текущего состояния.

## Маршрутизация и проверка трафика

WARP скрывает реальный выходной IP VPS от российских сайтов и приложений. Через него направляются `.ru`, `.su`, `.рф` (`domain:xn--p1ai`), `geosite:category-ru` (включая сервисы в других доменных зонах) и `geoip:ru` (в том числе обращения по IP). Нужны актуальные `geosite.dat` с категорией `category-ru` и `geoip.dat` с категорией `ru`; отсутствие категорий — ошибка, а не повод убрать защиту.

Порядок: служебный API и существующие выходы `blackhole` → российские домены → российские IP → остальные пользовательские маршруты. Таким образом, обычное правило `direct` не обходит WARP для российских ресурсов; относительный порядок внутри каждой группы сохраняется. Неоднозначный catch-all в середине списка или завершающий запрет вызывает ошибку до сохранения. `routing.domainStrategy=IPOnDemand` позволяет проверять IP домена до прямого выхода; `IPIfNonMatch` с прямым catch-all этого не гарантирует.

Домен определяется из запроса клиента или sniffing, IP — непосредственно либо через DNS. При недоступности WARP совпавшие запросы завершаются ошибкой: fallback на `direct` не добавляется. Остальной трафик сохраняет обычные маршруты; это не глобальный VPN для VPS. Списки не гарантируют распознавание всех российских владельцев: неизвестный домен на зарубежном IP может не совпасть. Полноту покрытия нужно проверять и дополнять для нужных сервисов; WARP не означает полной анонимности.

Финальная проверка standalone запускает временный локальный клиент Xray и получает HTTPS-ответ через выбранный VLESS/Vision/REALITY или VLESS/XHTTP/REALITY inbound. Дополнительно проверяются правильный SNI, чужой SNI, ClientHello без SNI, согласование `h2` через ALPN, HTTP→HTTPS redirect и отсутствие страницы панели на fallback. Отдельная проверка WARP требует `warp=on` или `warp=plus` в Cloudflare trace. Этот диагностический запрос к Cloudflare проходит через WARP только во временном процессе; рабочие правила остаются выборочными для российских ресурсов. Временный процесс и файлы удаляются при завершении. Ошибка любого обязательного теста не позволяет объявить установку успешной.

## Импорт пользователей 3x-ui

Получите SQLite-бэкап через панель или создайте согласованную копию на исходном VPS. Передайте копию на новый VPS по SSH и ограничьте доступ к файлу владельцем.

```bash
sudo sqlite3 /etc/x-ui/x-ui.db ".backup '/root/x-ui-migration.db'"
sudo chmod 600 /root/x-ui-migration.db
```

На новом VPS выберите пункт 3, укажите путь к копии и выберите Vision или XHTTP. Если в базе несколько VLESS inbound, мастер покажет их ID и попросит выбрать один. Переносятся UUID, subId, состояние, доступные лимиты, сроки и счётчики использования. При ошибке импорта скрипт возвращает базу нового VPS к состоянию перед импортом. Исходная копия открывается только для чтения.

Для нового VPS создаются свежие ключи REALITY и адреса подписок. Клиентам потребуется обновить профили. Настройки панели, другие inbound, правила маршрутизации, параметры устройств и привязки к внешним хостам настраиваются отдельно. Проверьте рабочее подключение тестового пользователя перед переключением остальных.

## Зашифрованные ссылки подписок

Для самостоятельного Vision или XHTTP мастер предлагает включить зашифрованные ссылки HAPP и INCY. Нажатие Enter включает оба формата, а ответ `no` сохраняет обычный HTTPS URL. HAPP формируется встроенным локальным кодеком 3x-ui, INCY — локальным кодеком crypt1. Оба формата следует передавать как секреты доступа. У INCY общий ключ приложения опубликован в кодеке, поэтому crypt1 скрывает URL при пересылке и открывается любым совместимым клиентом. Для Mihomo используется его собственная HTTPS-подписка. [Формат INCY](https://docs.incy.cc/en/deep-links/#encrypted-crypt1-links) · [Официальный кодек INCY](https://github.com/INCY-DEV/incy-link-encoder)

## Транспорты

`Vision` — основной профиль: `network=tcp`, `flow=xtls-rprx-vision`, REALITY и локальный self-steal. Он рассчитан на максимальную пропускную способность и меньшее количество транспортных состояний.

`XHTTP` использует то же локальное REALITY self-steal, `network=xhttp`, пустой `flow`, `mode=auto` и XMUX. Мастер выбирает один транспорт на сервер и сохраняет его для восстановления.

`AmneziaWG` берёт пакеты из официального PPA, а значения профиля из актуального стабильного релиза AmneziaVPN. Установщик проверяет действующие параметры ядра перед открытием порта. Минимальная поддержка соответствует профилю AWG 3.1. Если формат исходных настроек существенно изменится, установка остановится с диагностикой. Восстановление использует сохранённый профиль, чтобы действующие клиенты сохранили доступ.

Импортируйте `/etc/xhttp-vps-awg/client.conf` в актуальный совместимый клиент AmneziaWG. Профиль направляет IPv4 и IPv6 в туннель, шлюз выпускает в Интернет IPv4. Конфигурация рассчитана на одно активное устройство с этим ключом. [Документация AmneziaWG](https://docs.amnezia.org/documentation/amnezia-wg/)

`Hysteria 2` принимает соединения по UDP/443 с проверяемым TLS-сертификатом. UDP обслуживает сайт по HTTP/3, а Nginx предлагает HTTP/3 в заголовке Alt-Svc на TCP/443. Импортируйте URI из `/root/xhttp-vps-hysteria.uri` в совместимый клиент. Для обоих UDP-режимов WARP, подписки 3x-ui и режим удалённой ноды недоступны.

## Обновления и перезагрузка

Во время первоначальной установки выполняется `apt-get dist-upgrade`, поэтому свежий VPS получает доступные обновления, включая изменения зависимостей и ядра. При ошибке установки пакетов мастер пытается исправить состояние `dpkg` и зависимости через APT и повторяет операцию. При сетевых сбоях он повторяет загрузки, а при ошибке запуска VPN-службы сбрасывает состояние ошибки systemd и пробует снова. Если новое ядро или системная библиотека требует перезагрузки, мастер завершает настройку и сообщает об этом.

Таймер `xhttp-vps-maintenance.timer` запускает обслуживание каждый день в 05:30 по выбранному IANA-часовому поясу. По умолчанию используется `Europe/Moscow`. Каждый запуск обновляет индексы APT и устанавливает исправления безопасности Ubuntu через `unattended-upgrade`. Устанавливаются все доступные исправления безопасности, включая критические. В воскресенье то же обслуживание устанавливает остальные обновления APT, разрешает установку новых зависимостей и запускает `autoremove` и `autoclean`.

После обновлений проверяются APT, dpkg, Nginx, SSH и выбранная VPN-служба. В режиме по умолчанию сервер перезагружается сразу после успешного обслуживания, если существует `/var/run/reboot-required` и другая задача APT уже завершилась. Режим `security` устанавливает только ежедневные исправления безопасности и оставляет перезагрузку ручной. Режим `none` отключает автоматическое обслуживание.

Еженедельный режим обновляет пакеты из настроенных APT-источников, включая AmneziaWG при наличии его PPA. Он также проверяет последние стабильные релизы 3x-ui и Xray-core для Vision и XHTTP либо Hysteria 2 для одноимённого транспорта. Установщик проверяет SHA-256 перед заменой и перезапускает службу только при обновлении. Для 3x-ui он сохраняет снимок SQLite, включая пользователей и настройки. Если запуск или проверка портов завершается ошибкой, установщик восстанавливает прежние файлы и базу 3x-ui и повторно запускает службу. При ошибке загрузки или после успешного восстановления обслуживание завершается, если служба работает, а следующая попытка обновления выполняется в очередное воскресенье. Обновления и возможное восстановление прерывают активные VPN-соединения.

Для действующей установки откройте актуальный установщик и выберите `4) Refresh automatic maintenance`. Пункт сохраняет ранее выбранные режим и часовой пояс. В недельном режиме новые проверки начнутся в следующее окно обслуживания.

Проверка расписания и журнала:

```bash
systemctl list-timers xhttp-vps-maintenance.timer
journalctl -u xhttp-vps-maintenance.service --since '30 days ago'
```

Пропущенное недельное окно обслуживания не вызывает дневную перезагрузку. Сертификат Let's Encrypt обновляется отдельным timer Certbot, который перечитывает TLS у Nginx и в соответствующей VPN-службе.

У пустой ноды тест VLESS явно помечается `SKIP`: требуется клиент из главной панели. WARP при включении проверяется и на пустой ноде. Локальный тест не проверяет внешний firewall и доступность VPS из сети клиента. Проверка Fail2ban требует активный daemon и jail `sshd`; для публичной панели дополнительно загружается jail `xhttp-vps-panel` по журналу `x-ui.service`.

## Маскировка и границы модели

Конфигурация уменьшает очевидную поверхность VPN: на TCP/443 остаётся обычный TLS-сайт, REALITY использует локальный self-steal, а subscription backend не публикуется напрямую. Публичная панель работает отдельно на случайном порту и длинном пути; allowlist/localhost позволяют скрыть этот порт. Nginx не пишет access log и не раскрывает версию в заголовках. SNI в REALITY — тот же домен, который обслуживает локальный Nginx; обычный или не прошедший REALITY ClientHello попадает на собственный cover-site. Чужой и отсутствующий SNI также не должны раскрывать панель. Не меняйте REALITY target на случайный внешний сайт: при неуспешной авторизации сервер может превратиться в нежелательный forwarder, а сетевой профиль станет зависеть от чужой инфраструктуры.

На Nginx с поддержкой `ssl_reject_handshake` TLS с чужим или отсутствующим SNI отклоняется. Штатный Nginx Ubuntu 22.04 выдаёт в том же случае отдельный нейтральный сертификат на `localhost`. На HTTP-запросы с чужим Host сервер отвечает 404. На правильном SNI установщик проверяет доверенный TLS и ALPN `h2`. В Hysteria 2 строгая проверка SNI действует и на UDP/443.

Наблюдателю по-прежнему доступны IP, ASN, открытый SNI, объём и время соединений. Блокировка UDP, адреса или подсети может остановить работу даже при корректной маскировке. Локальные проверки оценивают поведение сервера. Для оценки доступности проверьте HTTPS, публичные порты и рабочее соединение с каждого нужного провайдера.

- отдельный домен без Cloudflare proxy (DNS only), корректный TLS и правдоподобный, быстрый cover-site;
- только необходимые входящие порты; панель — localhost/Tailscale либо строгий allowlist;
- SSH-ключи вместо пароля; после проверки отдельного sudo-пользователя можно запретить password login и прямой root login, не меняя SSH одновременно с первой установкой VPN;
- актуальный Xray/3x-ui после тестирования обновления, регулярная проверка CVE и резервная копия перед обновлением;
- уникальные UUID/subId для каждого пользователя, немедленная блокировка потерянного устройства и отсутствие общих подписок;
- отсутствие секретов в публичных логах, issue и скриншотах; state/result-файлы остаются `0600` и доступны только root;
- мониторинг необычного трафика, диска, памяти и входов SSH без записи полных subscription URL.

Не включайте случайные `fragment`, `finalmask`, нестандартные TLS-заголовки и постоянно меняющиеся padding-настройки только ради «маскировки»: они могут добавить устойчивый отпечаток, ухудшить совместимость или открыть уязвимость. XHTTP-параметры меняйте только по документации текущей версии и с внешним тестом из нужных сетей.

## Профиль памяти 3x-ui / XHTTP

Новая установка и восстановление применяют общие `bufferSize`/`connIdle` для обоих транспортов. Настройки XMUX применяются только к XHTTP:

| Параметр | Значение | Где действует |
|---|---|---|
| `policy.levels.0.bufferSize` | `64` КиБ | Буфер внутренних pipe Xray уровня 0 |
| `policy.levels.0.connIdle` | `180` секунд | Простой проксируемой сессии уровня 0 |
| `xmux.maxConcurrency` | `"0"` | Только XHTTP: отключает выбор пула по concurrency |
| `xmux.maxConnections` | `"1"` | Размер клиентского пула XMUX |
| `xmux.cMaxReuseTimes` | `"0"` | Без ограничения по этому счётчику |
| `xmux.hMaxRequestTimes` | `"300-600"` | Порог запросов для смены транспорта |
| `xmux.hMaxReusableSecs` | `"600-900"` | Окно повторного использования транспорта |
| `xmux.hKeepAlivePeriod` | `0` | Значение по умолчанию ядра |

Это снижение нагрузки на память, а не исправление доказанной утечки в Xray. `bufferSize` не выделяется целиком каждому TCP-сокету и не ограничивает всю память процесса; линейную экономию по числу ESTAB обещать нельзя. `connIdle` не закрывает простаивающий внешний HTTP/2 transport. `hMaxReusableSecs` проверяется при выборе транспорта; активные запросы могут пережить этот срок. `maxConnections=1` не является жёстким пределом общего числа сокетов при ротации.

XMUX хранится в inbound панели для передачи клиентам через подписку. Обновите подписки и переподключите клиентов; на ноде проверьте также профиль, выдаваемый главной панелью. Строковые значения сохраняют совместимость экспорта в Mihomo. Старые клиенты могут игнорировать эти поля. Остальные уровни policy не меняются.

Для уже работающего сервера, установленного этим проектом, скопируйте `optimize-xhttp-memory.sh` рядом с установленными скриптами и выполните:

```bash
sudo bash /root/optimize-xhttp-memory.sh
```

Скрипт читает локальный state-файл и обновляет policy уровня 0. Для XHTTP он также обновляет XMUX inbound `in-443-xhttp-reality`; для Vision сохраняет transport без изменений. Клиенты, ключи, пути, лимиты и маршрутизация не сбрасываются. Перед записью создаётся закрытая папка `/root/xhttp-memory-backup.*` с online-копией SQLite и исходными JSON. При уже применённом профиле повторный запуск ничего не меняет. При изменении выполняется перезапуск Xray, текущие соединения могут оборваться. Не запускайте параллельно с редактированием панели.

Если сохранение частично завершилось, путь к резервной копии выводится в ошибке. Исходный `xray.json` можно вернуть через редактор Xray Configs, а `inbound.json` — через API update того же inbound. Восстановление полной БД делайте только при остановленном `x-ui`, сохранив текущее состояние и учитывая файлы WAL/SHM; это откат всех изменений панели после копии.

Сравните RSS, swap, FD, ESTAB и goroutine при сходной нагрузке до изменения, через 30 минут и через сутки. Снижение сразу после рестарта само по себе не доказывает устранение утечки. При тысячах внешних H2-соединений потребуется также обновление/исправление ядра или клиентского транспорта; регулярные рестарты и `MemoryMax` не заменяют диагностику.
